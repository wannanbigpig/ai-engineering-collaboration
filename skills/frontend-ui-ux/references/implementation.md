# 把界面目标变成可施工规格

在设计方向仍停留在形容词、或不知道如何接通与检查页面时读取相关部分。局部修改复用已有决定，不必重新完成整份说明；只要方案或只读评估时，不据此转为实施。

## 从任务中确定实现依据

把当前任务落实到能画出或实现的决定，保留在会话或已有任务记录中即可：

| 需要决定的内容 | 可实施的表达 |
| --- | --- |
| 页面任务 | 用户先看什么、比较什么、执行什么操作；哪个结果表示任务完成 |
| 页面骨架 | 首屏有哪些区域、谁主谁次、内容如何分组、主要动作放在哪；窄屏如何重排 |
| 视觉规格 | 使用哪些颜色角色和实际 token/色值，标题、正文、标签如何区分，容器、间距、边界如何统一 |
| 组件行为 | 真实字段、单位、按钮归属、反馈位置，以及本次受影响的禁用、加载、错误和成功行为 |
| 内容与素材 | 哪些事实、文案和图片已经提供；哪些缺口可以通过排版解决，哪些确实影响交付 |
| 运行入口 | 从仓库配置确认的启动命令、实际页面路由、所需测试数据及可执行的主要操作 |

例如，“筛选区更清楚”还不能施工；“把筛选字段和筛选按钮放入同一工具区，退款字段与提交反馈留在独立任务区，窄屏按原操作顺序换行”已经说明要改的关系。具体尺寸继续沿用目标项目的组件和 token，不另造一套默认值。

有设计稿时将其对应到真实内容、组件和可运行行为；没有设计稿时自行作出协调的选择，不把“稍后美化”当作视觉规格。新页面和已有业务页的具体例子见[落地场景](examples.md)。

## 按选定规格接通页面

将骨架、视觉和一条真实用户路径一起落地：把内容放到语义结构中，将视觉选择写入现有样式层，连接实际事件、数据变化和反馈。一个只切换按钮文字的处理器，不等于预约、退款或保存已经实现。

从 README、项目脚本、路由和现有测试设施确认运行方式。使用仓库已有的命令和包管理器，启动后以真实输出的地址和目标路由打开页面，确认加载的是本次实现及所需内容。不要为获得一张预览另换技术栈；静态页面和带 API 的应用按各自已有入口运行。

验证可使用任务允许的本地夹具、模拟服务或测试环境，但反馈应反映它们的真实返回，交付时说明模拟范围。用户提供了预约入口，就核对导航目标；要求页内提交，就接通任务规定的提交与反馈契约。

## 将渲染结果转回修改

观察实际页面并执行受影响路径，把问题落实到结构、样式或行为，而不是只列审美判断：

| 观察到的问题 | 对应的修正方向 |
| --- | --- |
| 两个动作看不出归属 | 调整分组、标题、字段与按钮位置，核对真实表单和事件边界 |
| 长标题、单位或错误提示挤坏布局 | 核对实际容器宽度、换行、最小宽度和反馈区域；保留必要内容 |
| 窄屏出现整页横向滚动 | 定位导致溢出的元素，调整其布局或容器；确需横向查看的内容使用局部滚动 |
| 点击后没有任务要求的反馈 | 跟踪事件与请求/导航，接通等待、结果或恢复路径，而非只增加 hover 效果 |
| 对话框关闭后键盘位置丢失 | 在本次受影响流程内核对焦点回到触发处及后续操作顺序 |
| 代码规格看似正确，页面主次仍不清楚 | 调整实际字号、字重、分组距离、对比或内容比例，依据渲染结果判断 |

优先修正阻塞任务和内容错误，再处理结构与视觉细节；批量修改后在相同视口和路径复核。不要给每个 CSS 微调单独做一轮截图，也不要用固定轮数停止尚未完成的必要修复。

截图须实际打开核对，页面操作须实际执行。不能访问目标、数据或状态时，保留真实失败与未验证范围；结论区分功能检查、视觉观察和交互实测。
