# 从页面任务落实到实现

在不知道如何把设计方向变成版式、样式和控件行为时，查相关例子；局部明确修改不必读取全部。以下业务前提、布局和数值用于解释取舍，不是当前项目事实、已验证结果或通用页面模板。项目已有 token、组件、品牌与明确设计要求优先。

若还不能把目标落实到施工规格，按需参考[实现与渲染闭环](implementation.md)。小范围调整复用已有决定，不必重新规划整页。

## 已有业务界面：分清筛选和退款提交

示例前提：现有页面已支持按订单号、状态筛选记录，也支持输入订单号和金额提交退款。已核对两者分别调用查询接口与退款接口，但控件挤在同一区域。任务是改善视觉与操作关系，保持接口和业务能力。

### 先确定骨架和动作归属

筛选属于“找记录”，退款属于“执行操作”，用空间和表单边界表达这种区别：

```text
退款记录
订单号 [输入框]  状态 [选择框]  [筛选]
列表：订单号 / 金额 / 状态 / 已有行操作

退款申请
订单号 [保留原有输入方式]
退款金额（元） [金额输入框]
字段错误或提交反馈
[提交退款]
```

这是上下排列的一种选择。若项目已有详情抽屉、侧栏表单或固定工具栏，优先延续它；若退款必须先选中订单，就保留选择与上下文关系，不把它改成上图的独立输入。拆分视觉区域前也要核对真实表单与提交事件，不能仅凭控件看起来挨在一起就改数据流。

### 把规格落实到现有组件

| 部分 | 具体处理及依据 |
| --- | --- |
| 标题和正文 | 沿用相邻业务页的页面标题、区块标题、表单标签和数据文本角色；例如既有正文为 14–16px、区块标题为 18px，就复用其角色，而非为这一页引入新字体 |
| 间距 | 相关字段采用紧密间距，两个任务区之间采用更大的区块间距；若现有尺度为 8/16/24/32px，可用 16px 组织字段、32px 分隔任务区，再用实际标签长度核对 |
| 动作层级 | 将“筛选”与“提交退款”放进各自的任务区；使用已有按钮变体表达层级，避免仅靠旁边一段说明区分提交目标 |
| 字段 | 保留可见标签、金额单位和原校验语义；同一字段的输入、帮助与错误在视觉上相邻，错误信息与控件建立可访问关联 |
| 提交中 | 使用原有提交状态防止重复操作，反馈放在提交动作附近；不要让加载文本消失后留下宽度跳变，也不要阻断无关的筛选操作 |
| 失败与成功 | 字段错误指向对应输入，服务失败保留已填内容并说明已有的恢复方式；成功反馈与真实返回结果一致，不提前显示完成或擅自清空上下文 |
| 窄屏 | 字段无法保持标签与输入可读时换行；列表确需横向滚动时把滚动限定在列表容器内，保留可辨认的列和操作，避免整页溢出 |

上述数值只解释间距与层级关系。已有组件的规格满足任务时直接用，不用另建一套 CSS token。

### 实施、运行，再按可见问题修正

从 `package.json`、README 或现有开发入口核对启动方式，沿用仓库的包管理器与服务。打开实际路由，确认页面及测试数据已加载；静态截图不能替代查询、退款与反馈路径的执行。涉及提交的检查使用已获准的测试环境或现有夹具。

渲染后把发现转成具体修正，例如：

- 如果两个动作仍难区分，检查标题、容器和按钮归属，调整这些关系，而不是继续补操作说明。
- 如果长错误文本把按钮推到输入旁边，修改表单布局，让错误占据明确的反馈区域；保留错误内容和可访问关联。
- 如果窄屏金额输入挤压单位，调整字段换行和宽度，而不是缩小全页字体。

将同一轮可见的关键问题合并修正，然后回到相同视口与操作路径检查改动。退款请求的 HTTP 方法、字段、权限、幂等和错误语义仍按已有契约验证；布局改善本身不能证明这些行为未退化。

## 新内容页：让家长快速找到合适的活动

示例前提：用户提供图书馆活动的真实名称、时间、地点和介绍，要求做一个易读页面。没有提供报名接口、预约状态或余票数据。主要读者是寻找活动信息的家长，不能仅因内容面向儿童就把操作界面做成幼儿游戏。

### 从内容决定页面结构

让读者先理解有哪些活动，再找到各活动的时间与地点。一种可实现的骨架是：

```text
已有馆名或标识                          已有导航

活动集合标题             提供的活动图片（若有）
简短导语

活动名称                 时间与地点
活动介绍与必要说明

下一项活动名称           时间与地点
活动介绍与必要说明

用户已提供的联系或交通信息（若有）
```

这里选择连续的活动内容区，使时间、地点容易逐项比较；不是先放一个通用大横幅，再把所有事实塞进等大的卡片。内容较多、读者需要筛选时可以采用其他结构，但应说明它帮助哪项查找任务。活动顺序依用户要求或已提供的真实时间，不猜日期、适龄、收费和剩余名额。

### 给出一份可施工的视觉规格

如果项目没有既定视觉系统，可以做出明确选择，而不把所有选择继续留给“稍后美化”。例如以下是一份方向，真实任务可采用完全不同的表达：

- 以深绿色 `#163B30` 承担标题与正文、浅色 `#F4F7F2` 承担页面背景、暖色 `#A54132` 承担已有链接或动作的强调；说明文字也要保持可读。实际渲染后检查这些角色之间的对比，不把写了色值当作已通过可访问性检查。
- 让集合标题的排版成为本例的视觉重点：标题、简短导语和首项活动形成连续阅读顺序，活动名称明确强于说明文字，时间地点位置稳定，便于横向比较。留白用来突出这个关系，不给每段内容叠加同等醒目的装饰。
- 使用项目已有字体或适合内容语言的系统字体栈。正文可从 `16px / 1.6` 起步，页面标题可用 `clamp(28px, 4.5vw, 48px)` 建立尺度差，活动标题比正文更醒目；用真实长标题核对换行与主次。
- 容器可从 `68rem` 最大宽度起步。有合适图片时，宽屏首屏的文字/图片可采用 `3fr / 2fr` 的列比、顶部对齐，让标题先被读到，图片保持其内容所需的比例；没有图片则由标题与活动内容组织版面。首项活动的重要信息应容易找到，不用固定满屏高度把它推到很远。
- 活动内容区可将名称/介绍与时间地点分栏，左边缘保持一致；窄屏改为“活动名→时间地点→介绍”的顺序，与 DOM 阅读顺序一致。段落保持适合实际语言的行宽，而不是把正文铺满整个显示器。
- 区块留白要比区块内部更充裕；例如内部 12–16px、活动之间 32–48px，再依据内容密度调整。边界、图标和图片采用同一套处理，避免每项活动都获得不同的装饰语言。
- 有提供的图片时，明确图片是在说明活动内容还是营造氛围，按这个用途选择尺寸与裁切。没有可用图片时可让排版和内容组织承担表达，不伪造活动照片、评价或参与人数。

这些是可替换的示例数值，不是图书馆、儿童页面或所有新页面的默认主题。已有品牌色、明确设计稿与用户指定的字体优先。

### 内容页与预约操作分开核实

只有介绍需求时，把内容完整、易查找地呈现出来即可。若用户提供已有预约链接并要求入口，按钮清楚说明会进入预约页面，并使用真实目标；若要求页内预约，则还需现有的可选场次、表单和提交契约，不能仅做一个点击后显示“预约成功”的按钮代替完整功能。

打开实际页面，检查活动名称、时间和地点可见且与输入一致；有链接才执行导航，有预约功能才验证其选择、提交和实际反馈。若窄屏图片把关键活动信息推得过远，缩短图片区域或重排内容；若所有文字等重，先调整标题、时间地点与介绍的尺度和分组。将修正落实到组件和样式后，再看相同页面，而不是只在说明中声称已经改善。

## 只读、仅方案与明确文案修改

| 请求 | 当前动作 | 完成边界 |
| --- | --- | --- |
| 只读评估布局与操作 | 查看实际页面与受影响流程，给出有依据的规格和建议 | 不修改源码或项目记录；截图证据放在任务允许的位置 |
| 只要设计或实施方案 | 给出结构、视觉规格、组件行为、运行与验收方式 | 返回可实施的方案，不自动写页面、创建项目文件或部署 |
| 仅将“提交”改成“保存” | 核对词义、已有状态文本和直接溢出风险 | 不额外发起设计阶段或全站改版；存在真实语义冲突时说明证据 |
| 只读审查表单代码 | 用审查能力核对归属、标签和行为契约 | 不因文件是前端代码自动转为视觉重设计 |
