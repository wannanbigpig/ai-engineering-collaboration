# 验证关卡

任何“完成、修复、通过、可发布”声明前，必须有新鲜、完整、可复核的证据。

## 流程

1. **定义证据**：列出直接证明结论的测试、Lint、类型检查、构建或业务路径命令，并说明各自证明什么。
2. **重新运行**：确认工作区、依赖和配置后运行完整命令，不依赖历史输出或他人转述。
3. **检查结果**：核对完整输出、断言和退出码；输出缺失时重新获取。
4. **区分类型**：测试、Lint、类型、构建和业务路径分别判断，不能用一种通过替代另一种。
5. **验证项目一致性**：运行项目声明的 formatter、Lint、类型检查和相关测试，核对本次实现与风格基线。UI 发生变化时，在可用环境中打开实际页面，对照同类页面检查组件、布局、设计令牌、交互、响应式及加载/空/错误状态；编译或构建通过不能替代视觉验证，无法运行时明确标记 UI 未验证。
6. **检查结构质量**：在本次 diff 和受影响范围内检查新增的等价逻辑、无依据的文件/函数/分支、平行实现、死代码、临时兼容层、错误掩盖和过度拆分；评估调用层级、跨文件跳转、参数传递与上下文恢复成本。函数长度只作为调查信号；单次使用且只转发参数或改名的小函数，如果没有独立业务语义、真实复用、清晰的测试/副作用边界或实质复杂度收益，应就近保留或内联。优先使用项目已有工具，必要的结构调整必须保持行为并可独立验证。不要默认扫描全仓、强制抽象合理重复，或为美观扩大任务范围。
7. **核对量化结论**：重复率、圈复杂度、覆盖率、漏洞数等数字必须附实际执行的工具、版本、范围和输出；未运行对应工具时只能给出定性观察并标记“未验证”，不得把模型估计写成测量结果。
8. **决定声明**：功能证据、项目一致性与适用的结构证据覆盖关键点且通过才宣称完成；部分通过要说明范围。

## 未验证

因环境、依赖、权限或外部系统无法验证时，明确写“未验证”，说明原因并给出可执行的后续命令；存在未完成验证时不得宣称完成。禁止以删除或弱化测试、跳过校验、吞异常或硬编码通过测试的方式制造“通过”证据。
