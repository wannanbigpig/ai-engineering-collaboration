# 需求定界

在开始设计或实施前，收敛会改变任务行为、范围、风险或验收方式的决策；目标是消除关键假设，不是进行无限追问或为每项小改动设置审批门槛。

## 触发与边界

出现任一情况时使用：

- 用户目标有多种合理解释，且不同解释会导致不同实现、数据范围或权限行为。
- 成功条件、非目标或验收方式不明确。
- 新功能、跨模块改动或不可逆操作缺少会影响方案的业务决策。
- 用户明确要求澄清、拆解需求或比较方案。

目标明确、影响局部且验证方式清晰的任务直接处理；能从代码、日志、规则或文档确认的事实先自行核对，不把检索工作交给用户。不要强制生成 Spec、ADR、待办或要求用户批准每一步。

## 澄清过程

1. **先建立事实基线**：读取相关规则、现有实现、测试和已知约束，区分已确认事实与待决事项。
2. **筛选关键决策**：只保留会实质改变范围、行为、风险或验收的未决问题；其余采用合理假设并显式说明。
3. **逐项收敛**：每次只询问一个关键问题，说明它影响什么；存在明显权衡时给出可选项和推荐方案。用户可随时选择停止澄清并授权某个假设。
4. **输出定界结论**：用简短清单记录目标、非目标、验收标准、已决事项、仍在采用的假设，以及下一步需要的 Skill 或行动。

## 后续路由

- 结论涉及跨文件、模块、数据流、权限或契约时，转 `change-impact-analysis`。
- 已确认要实施功能或 Bug 修复时，转 `test-driven-change`；本地异常先转 `systematic-debugging`。
- 用户只需要方案、比较或问题清单时，交付定界结论后停止。

每次路由只说明确有必要的下一步；不要因为本 Skill 被调用而自动加载全部工程流程。

## 完成标准

在无需猜测关键业务决策的前提下，可以说明任务目标、边界和验收方式；仍有未决事项时，明确其影响与需要用户决定的内容，不宣称需求已完全确定。
