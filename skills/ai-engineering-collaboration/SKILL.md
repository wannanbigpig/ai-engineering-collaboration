# AI 工程协作

这是完整工程任务的主入口。用户只需调用本 Skill；本入口始终负责规则、计划、记录、专项阶段整合和最终验证，不把治理责任转交给用户。目标是在满足正确性和风险边界的前提下，用最少的有效循环完成工作。

## 工作原则

- 先确定成功条件和最小影响范围，再收集足以决定下一步的证据；不要为未提出的未来需求扩展方案。
- 合并可并行的只读检查；不要重复读取未变化的文件、重复运行已通过且输入未变化的验证，或为了形式完整增加工具调用。
- 每次准备进入新一轮调查前，先说明尚缺哪条会改变决策的证据；没有此类证据时结束调查并执行或汇报。
- 开始修改前，以及以先前调查为依据进入新阶段前，刷新相关工作区状态：Git 项目核对 `git status` 与目标差异，重新读取目标文件及直接关联实现或测试；不得假定代码未变化。发现与当前结论相关的更新时，停止沿用旧判断并按最新状态重估范围和验证；无关改动保留不碰。

## 规则发现与澄清

1. 先发现可能约束目标路径的 `AGENTS.md`、`AGENTS.override.md`、`CLAUDE.md`；路径越近的规则优先。存在 `.aitasks/lessons.md` 时，按任务关键词检索标题与场景并读取命中内容；无内容检索能力时读取最小相关范围，禁止默认整篇加载。
2. 能由代码、日志、测试或规则确认的问题先自行调查。只有仍存在会显著改变行为、风险或范围的不确定性时才停止相关修改，一次询问一个关键问题。
3. 已接入 CodeGraph MCP 且任务涉及代码结构、调用链、依赖或影响范围时，优先用它定位定义和调用方；结果仍须以实际代码、日志和测试交叉确认。

## 任务分级

默认直接处理目标明确、影响局部且验证清晰的任务；文件数量本身不决定复杂度。仅在存在跨模块行为变化、重要数据流或权限/安全/事务/并发风险、需求歧义、不可逆操作，或无法预先定义验证方式时按非平凡任务处理。

## 规划

非平凡任务必须先加载 `aitasks-maintenance` 创建或更新 `.aitasks/todo.md`，记录目标、影响范围、执行步骤、验证方式、风险、当前进度和最终结果；在阶段边界和结论变化时更新，不按单个工具调用记录流水账。出现用户纠正、Bug 或 CI 根因、测试/构建失败根因、隐藏项目约定，或可复用排查与验证方法时，加载 `aitasks-maintenance` 向 `.aitasks/lessons.md` 追加可复用经验。

实际实现与预期不符、测试或构建失败、影响范围扩大、发现新业务风险，或继续执行会形成明显补丁化处理时，立即停止当前实施：保留证据、更新 todo，并重新判断需求、影响、根因和验证方式。简单任务不因入口被调用而强制创建 todo。

## 路由决策

本入口是唯一的主处理 Skill。先确认当前环境中可用的专项 Skill，再按以下优先级选择一个**内部执行阶段**；用户不必手动点名。用户明确点名且该 Skill 可用、与任务不冲突时优先采用；点名的 Skill 不可用时如实说明，并按下表选择当前可用的最接近能力，不假定外部 Skill 已安装或可被自动调用。

| 优先级 | 明确触发条件 | 内部执行阶段 |
|---|---|---|
| 1 | `.aitasks` 的计划、经验、归档或元数据维护 | `aitasks-maintenance` |
| 2 | 明确只读代码审查 | `code-review` |
| 3 | 远程 CI 或构建流水线失败归因 | `ci-triage` |
| 4 | 本地 Bug、测试/构建失败、性能或集成异常，且根因未明 | `systematic-debugging` |
| 5 | 目标、范围、验收标准或关键业务决策存在会改变执行结果的歧义 | `requirements-framing` |
| 6 | 已确认方案、Spec 或任务清单需要实施 | `plan-execution` |
| 7 | 尚未实施，且需要先判断跨文件、模块、仓库、数据流、权限或契约影响 | `change-impact-analysis` |
| 8 | 新功能或 Bug 需要测试先行的变更闭环 | `test-driven-change` |
| 9 | 只需要高风险完成声明、发布前检查或严格验证证据 | `verification-gate` |

内部执行阶段完成其职责后，最多再附加两个确有必要的前置或后续 Skill：关键需求未定时先加 `requirements-framing`；实施前影响未知时先加 `change-impact-analysis`；实施过程需要测试先行时加 `test-driven-change`；完成后需要更高强度证据时加 `verification-gate`；需要独立只读审查时再加 `code-review`。远程 CI 先由 `ci-triage` 定位，确认是代码或本地可复现问题后才转 `systematic-debugging`；不要因为命中多个词就加载全部 Skill。专项 Skill 不可用时，本入口按其已知任务边界执行最小必要流程；只有缺少必须的外部访问或用户决策时才停止并说明。

每次路由先简短输出：

```text
路由决定
- 主入口：`ai-engineering-collaboration`
- 内部执行阶段：<名称，或“直接处理”>
- 附加阶段：<最多两个；没有则“无”>
- 触发依据：<任务事实>
- 未匹配处理：<直接处理、补充事实，或需要澄清的关键点>
```

目标明确、影响局部、验证清晰而未命中专项场景时，在本入口内直接处理，不为了填表强行套用 Skill。非平凡任务若尚无法可靠判断专项路由，先收集会改变决策的最小事实；只有关键需求决策仍未定时才使用 `requirements-framing`。专项 Skill 仍可按自身 description 独立触发，但不会替代本入口已经承担的治理职责。

## 子 Agent

用户已授权在符合以下条件时自主启动子 Agent：至少两个工作流没有顺序或数据依赖、不会写同一文件或共享外部状态，并且预期能明显缩短总耗时。只读分析、检索和独立验证可直接并行；实现任务只有在隔离工作区可用，或文件所有权、输入输出和集成顺序都已明确时才可并行。共享工作区的写入、数据库迁移、发布、推送、权限变更和不可逆操作由主 Agent 串行处理或先请求确认。

启动前说明子任务边界和预期产出；主 Agent 负责整合结果、刷新相关代码状态并复核冲突证据。上层规则禁止、用户明确禁止或条件不成立时不启动。

## 验证与停止条件

- 验证与风险成比例：局部变更运行最相关的专项测试；跨模块、高风险或发布任务再运行完整测试、构建、Lint 或类型检查。
- 验证失败时保留完整错误，形成一个可证伪假设并做最小实验；同一假设不以不同命令形式重复尝试。
- 成功条件已有新鲜证据、相关风险已说明且无必要工作剩余时停止。工具调用次数少不是目标，避免无决策价值的循环才是目标。

## 统一输出模板

无论使用此 Skill 的 Agent、模型或 Harness 是什么，最终交付一律使用 [assets/final-response.md](assets/final-response.md) 的五个二级标题，顺序和标题文字不得变更。标题必须同时适用于实施、分析、方案和审查，不得假定已修改文件：

- **交付结果**：实施任务说明已完成的行为；只读任务说明调查范围与结论；方案任务说明推荐方向。
- **关键内容**：实施任务列出关键变更；只读任务列出关键发现；方案任务列出关键决策。
- **依据与影响**：Bug/CI 任务说明根因；分析与审查说明证据和影响；不适用时写“无”。
- **核查与验证**：列出已执行的命令、检查或交叉核对；未执行时说明原因和可执行的验证方式。
- **风险与后续**：列出遗留风险、限制和需要用户决定的下一步；没有时写“无”。

`.aitasks` 的 todo 和经验模板由 `aitasks-maintenance` 唯一维护。需要创建或更新此类记录时，加载该专项 Skill 并使用其 `assets/todo.md`、`assets/lessons.md`；不得在本入口 Skill 复制或另建这两份模板。
