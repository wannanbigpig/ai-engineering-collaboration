# AI 工程协作

本入口只统筹需要跨多个专项阶段的工程任务；单一明确工作流直接处理或使用对应专项 Skill。目标是在满足正确性和风险边界的前提下，用最少的有效循环完成工作。

## 授权与只读边界

- 用户已明确要求修复或实施时，授权在阶段切换后继续有效，不因加载 Skill 再次确认；只有超出已有授权的实质范围或外部副作用需要用户决定时才询问。
- 用户要求只读或不修改文件时，计划与结论保留在会话中，不写 todo、经验、复用计数、`.gitignore` 或其他文件。分析阶段结束不自动转为实施。
- “核对”指 Agent 自行检查证据；“询问用户”仅用于不能从现有事实推导的必要决策。只暂停依赖该决策的工作。

## 工作原则

- 先确定成功条件和最小影响范围，再收集足以决定下一步的证据；不要为未提出的未来需求扩展方案。
- 合并独立只读检查；只补会改变方向、范围或结论的证据，不重复读取未变化的文件或运行输入未变且已通过的验证。
- 开始修改前或进入新阶段时核对相关工作区状态：Git 项目检查 `git status` 与目标差异；内容已变化、上下文缺失或存在并发修改迹象时才重读相关文件。发现相关更新时重估范围和验证，无关改动保留不碰。
- 修改前建立局部风格基线，修改后核对本次变更范围的结构质量；各阶段复用已有证据，独立审查仅在需要时追加。

## 规则发现与澄清

1. 发现适用的 `AGENTS.md`、`AGENTS.override.md`、`CLAUDE.md`，复用未变化的已加载规则。工程任务开始调查时，若当前项目有 `.aitasks/lessons.md`，先用任务关键词轻量检索标题和正文，只读取命中记录，再展开代码、README 等调查；任务方向变化时按新关键词补查。经验是线索，路径和关键事实仍需核对当前环境；未命中直接继续，不默认整篇加载或触发维护。业务检索从已知目标开始，仅在关系缺失时扩大；隐藏目录中的适用规则和经验仍须核对。
2. 初次实现且上下文不足时，先看相关工具配置、相邻实现和共享设施；模式冲突或依据不足才补同类样本。依据依次为明确要求和契约、路径规则、项目工具、同类实现、仓库惯例、通用做法；仅关键业务行为、公开契约或偏好未定时询问。
3. 能由代码、日志、测试或规则确认的问题先自行调查。剩余关键问题可一次合并少量互不依赖的问题；答案会决定后续问题时才逐项询问。
4. 未明确的结构、调用或依赖关系可用已接入的 CodeGraph MCP 定位；已知文件和局部关系直接检索，重要结论以代码与测试核实。经验查询只读取命中标题和正文，到下一同级标题或记录元数据为止；元数据属于后续记录，缺失计数为“未记录”。普通查询不加载维护流程或附带不需要的计数。

## 入口选择与任务风险

风险独立判断：目标明确、影响局部且验证清晰的任务默认直接处理；涉及跨模块行为变化、重要数据流或权限/安全/事务/并发风险、实质需求歧义、不可逆操作，或无法预先定义验证方式时，按非平凡任务规划和验证。文件数量不决定风险，风险较高也不自动要求加载入口或委派。

## 规划

非平凡实施任务必须在修改前形成最小计划：目标、影响范围、下一可验证切片、验证方式和主要风险；存在真实依赖时说明先后条件。复用已有等价计划，缺少部分自行补齐；会话计划也有效，不因计划形式再次请求批准。只要任务会编辑项目代码，就使用 `aitasks-maintenance` 为本次任务创建或复用一条 `.aitasks/todo.md` 记录；纯文档修改可只保留会话计划。

阶段边界和结论变化时更新计划，不记录工具调用流水账。经验触发、去重和归档按 `aitasks-maintenance` 执行；只读限制仍优先。

非预期测试/构建失败、实际实现与方案不符或新风险使原判断失效时，暂停受影响的实施并重估；测试先行的预期失败和计划内诊断实验不触发重规划。简单代码编辑任务也按一任务一条 todo 记录，不扩写成冗长方案。

## 路由决策

通过本入口执行时，由入口统筹专项。先核对当前环境中可用的专项 Skill，再按以下优先级选择一个**内部执行阶段**；用户不必手动点名。用户明确点名且该 Skill 可用、与任务不冲突时优先采用；点名的 Skill 不可用时如实说明，并按下表选择当前可用的最接近能力，不假定外部 Skill 已安装或可被自动调用。

| 优先级 | 明确触发条件 | 内部执行阶段 |
|---|---|---|
| 1 | 任务本身是 `.aitasks` 写入、归档或元数据维护 | `aitasks-maintenance` |
| 2 | 明确代码审查，或需要核实收到的审查反馈 | `code-review` |
| 3 | 远程 CI 或构建流水线失败归因 | `ci-triage` |
| 4 | 本地 Bug、测试/构建失败、性能或集成异常，且根因未明 | `systematic-debugging` |
| 5 | 目标、范围、验收标准或关键业务决策存在会改变执行结果的歧义 | `requirements-framing` |
| 6 | 用户已要求实施现有方案、Spec 或任务清单 | `plan-execution` |
| 7 | 尚未实施，且共享行为、跨模块数据流或契约影响仍未明确 | `change-impact-analysis` |
| 8 | 新功能或 Bug 需要测试先行的变更闭环 | `test-driven-change` |
| 9 | 明确要求验证，或高风险交付、发布前仍有证据缺口 | `verification-gate` |

由入口选择一个当前阶段，只有尚存关键缺口才追加必要阶段；不因规则提到 Skill 名称而递归加载，也不重启已完成阶段。专项返回结论、证据和缺口。首次选择或路由实质变化时一句话说明原因，简单任务不输出路由表。根因未明才调试，共享影响未明才追加影响分析，需要回归保护才补测试策略，交付证据不足才追加验证关卡。

专项独立使用时继承授权和只读边界，不反向加载入口。未命中专项的明确局部任务直接处理；专项不可用时说明限制，在现有能力与授权内完成可执行部分。关键决策仍未定才需求定界。

## 子 Agent

仅在当前会话与上层规则允许、子任务可独立推进且收益超过协调成本时委派，不因任务非平凡而强制启动。启动前明确边界与产出；实现需隔离工作区或明确文件所有权、输入输出及集成顺序，共享写入与高副作用操作由主 Agent 在已有授权内串行处理；主 Agent 整合结果、刷新相关状态并复核冲突证据，委派不扩大授权。

## 验证与停止条件

- 验证与风险成比例：行为或交付物变化且现有证据不足时运行最小相关检查；跨模块、高风险或发布任务再扩大覆盖，纯文档或注释修改不默认运行无关测试。
- 非预期验证失败时保留相关完整异常链，形成一个可证伪假设并做最小实验；同一假设不以不同命令形式重复尝试。
- 成功条件已有新鲜证据、相关风险已说明且无必要工作剩余时停止。工具调用次数少不是目标，避免无决策价值的循环才是目标。

## 交付格式

用户指定格式优先；审查先列问题、后给摘要，简短结果直接交付。只有确需完整结构时才读取并使用 [assets/final-response.md](assets/final-response.md)。

`.aitasks` 模板由 `aitasks-maintenance` 唯一维护，新建只读取对应模板，更新状态或计数无需模板。
