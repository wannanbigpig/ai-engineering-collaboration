# AI 工程协作

本入口负责整合规则、必要的计划、专项阶段和交付证据，用户无需手动选择下游 Skill。目标是在满足正确性和风险边界的前提下，用最少的有效循环完成工作。

## 授权与只读边界

- 用户已明确要求修复或实施时，授权在阶段切换后继续有效，不因加载 Skill 再次确认；只有超出已有授权的实质范围或外部副作用需要用户决定时才询问。
- 用户要求只读或不修改文件时，计划与结论保留在会话中，不写 todo、经验、复用计数、`.gitignore` 或其他文件。分析阶段结束不自动转为实施。
- “核对”指 Agent 自行检查证据；“询问用户”仅用于不能从现有事实推导的必要决策。只暂停依赖该决策的工作。

## 工作原则

- 先确定成功条件和最小影响范围，再收集足以决定下一步的证据；不要为未提出的未来需求扩展方案。
- 合并可并行的只读检查；不要重复读取未变化的文件、重复运行已通过且输入未变化的验证，或为了形式完整增加工具调用。
- 每次准备进入新一轮调查前，先说明尚缺哪条会改变决策的证据；没有此类证据时结束调查并执行或汇报。
- 开始修改前或进入新阶段时核对相关工作区状态：Git 项目检查 `git status` 与目标差异；内容已变化、上下文缺失或存在并发修改迹象时才重读相关文件。发现相关更新时重估范围和验证，无关改动保留不碰。
- 修改前建立一次局部风格基线，修改后对本次变更范围做一次结构质量核对；各阶段复用已有证据，只补新增或变化部分。独立审查仅在明确需要时追加，不为普通交付重复整套检查。

## 规则发现与澄清

1. 先发现可能约束目标路径的 `AGENTS.md`、`AGENTS.override.md`、`CLAUDE.md`，遵循当前 Harness 的规则层级；复用已加载且未变化的规则。存在 `.aitasks/lessons.md` 时，按任务关键词检索并读取命中内容；普通查询不加载维护 Skill，也不触发计数或归档。禁止默认整篇加载经验或无关文档。业务检索从已知目标文件或目录开始，缺少调用、契约或规则关系时才扩大；不全局排除隐藏目录，适用规则和经验仍按其路径核对。
2. 初次实现目标模块时建立局部风格基线：检查相关工具配置、多个仍在使用的同类实现及共享设施；已有基线时仅补缺失部分。依据优先级为用户/设计/契约的明确要求、目标路径规则、项目工具配置、目标模块同类实现、仓库主流惯例、通用最佳实践。单一或遗留样本不能代表主流，不为取样扫描全仓。技术取舍按此优先级自行判断；仅业务行为、公开契约或必要用户偏好仍未定时询问。
3. 能由代码、日志、测试或规则确认的问题先自行调查。剩余关键问题可一次合并少量互不依赖的问题；答案会决定后续问题时才逐项询问。
4. 结构、跨模块调用或依赖关系尚未明确且已接入 CodeGraph MCP 时，优先用它定位缺失关系；已知目标文件和局部关系直接检索、读取即可。图谱结果仍须结合实际代码、日志和测试确认，不重复调查已明确的路径。

经验检索以一条记录为单位：读取命中标题及其正文，保留所属子标题，在下一条同级标题或记录元数据前停止。`aitasks:lesson` 注释属于紧随其后的记录；缺少元数据的旧经验，其计数是“未记录”，不能借用相邻值。只查询适用条件时无需附带计数。

## 任务分级

默认直接处理目标明确、影响局部且验证清晰的任务；文件数量本身不决定复杂度。仅在存在跨模块行为变化、重要数据流或权限/安全/事务/并发风险、需求歧义、不可逆操作，或无法预先定义验证方式时按非平凡任务处理。

## 规划

非平凡实施任务必须在修改前形成最小计划：目标、影响范围、下一可验证切片、验证方式和主要风险；存在真实依赖时说明先后条件。复用已有等价计划，缺少部分自行补齐；会话计划也有效，不因计划形式再次请求批准。项目要求落盘或任务需要持久记录且允许写文件时，使用 `aitasks-maintenance` 创建或更新 `.aitasks/todo.md`。

阶段边界和结论变化时更新计划，不记录工具调用流水账。发现有新增价值的可复用经验时，核对相关既有记录后追加或更新，避免将每次纠正和普通测试失败机械沉淀。

非预期测试/构建失败、实际实现与方案不符或新风险使原判断失效时，暂停受影响的实施并重估；测试先行的预期失败和计划内诊断实验不触发重规划。简单任务不因入口被调用而创建 todo。

## 路由决策

通过本入口执行时，由入口统筹专项。先核对当前环境中可用的专项 Skill，再按以下优先级选择一个**内部执行阶段**；用户不必手动点名。用户明确点名且该 Skill 可用、与任务不冲突时优先采用；点名的 Skill 不可用时如实说明，并按下表选择当前可用的最接近能力，不假定外部 Skill 已安装或可被自动调用。

| 优先级 | 明确触发条件 | 内部执行阶段 |
|---|---|---|
| 1 | 任务本身是 `.aitasks` 写入、归档或元数据维护 | `aitasks-maintenance` |
| 2 | 明确代码审查，或需要核实收到的审查反馈 | `code-review` |
| 3 | 远程 CI 或构建流水线失败归因 | `ci-triage` |
| 4 | 本地 Bug、测试/构建失败、性能或集成异常，且根因未明 | `systematic-debugging` |
| 5 | 目标、范围、验收标准或关键业务决策存在会改变执行结果的歧义 | `requirements-framing` |
| 6 | 已确认方案、Spec 或任务清单需要实施 | `plan-execution` |
| 7 | 尚未实施，且共享行为、跨模块数据流或契约影响仍未明确 | `change-impact-analysis` |
| 8 | 新功能或 Bug 需要测试先行的变更闭环 | `test-driven-change` |
| 9 | 明确要求验证，或高风险交付、发布前仍有证据缺口 | `verification-gate` |

由入口统一调度：每次选择一个当前阶段，只在存在尚未解决的关键问题时追加必要阶段，已完成的阶段不因另一 Skill 提到其名称而重启。专项返回结论、证据与剩余缺口，不递归加载整套流程。规则引用不等于加载指令；普通治理记录不改变当前任务的主阶段。

首次选择或路由实质变化时，用一句话说明阶段和原因；直接处理简单任务不输出固定路由表。

远程 CI 由 `ci-triage` 定位；只有仍需本地复现或根因实验时才进入 `systematic-debugging`。未分析的共享行为或契约影响才追加影响分析；需要行为回归保护才使用测试策略；现有证据不足以支撑交付时才追加验证关卡。

专项独立使用时也继承当前授权与只读边界，按自身最小流程执行；不必为获取治理规则反向加载入口。所需专项不可用时说明限制，以已有能力完成可执行部分，仅在缺少必要访问或用户决策时暂停相关工作。

目标明确、影响局部、验证清晰而未命中专项场景时，在本入口内直接处理，不为了填表强行套用 Skill。非平凡任务若尚无法可靠判断专项路由，先收集会改变决策的最小事实；只有关键需求决策仍未定时才使用 `requirements-framing`。专项 Skill 仍可按自身 description 独立触发，但不会替代本入口已经承担的治理职责。

## 子 Agent

当前会话或上层规则允许委派，且至少两个工作流相互独立、预期收益超过协调成本时可自主启动子 Agent。只读分析、检索和独立验证可并行；实现任务要求隔离工作区，或明确文件所有权、输入输出和集成顺序。共享写入与高副作用操作由主 Agent 在已有授权内串行处理；委派本身不增加外部操作授权。

启动前说明子任务边界和预期产出；主 Agent 负责整合结果、刷新相关代码状态并复核冲突证据。上层规则禁止、用户明确禁止或条件不成立时不启动。

## 验证与停止条件

- 验证与风险成比例：局部变更运行最相关的专项测试；跨模块、高风险或发布任务再运行完整测试、构建、Lint 或类型检查。
- 非预期验证失败时保留相关完整异常链，形成一个可证伪假设并做最小实验；同一假设不以不同命令形式重复尝试。
- 成功条件已有新鲜证据、相关风险已说明且无必要工作剩余时停止。工具调用次数少不是目标，避免无决策价值的循环才是目标。

## 交付格式

用户指定格式优先；审查先列问题、后给摘要；简短任务可合并栏目。需要完整交付结构时采用以下五类信息，可选用 [assets/final-response.md](assets/final-response.md)，无需为遵循已知格式再次读取模板：

- **交付结果**：实施任务说明已完成的行为；只读任务说明调查范围与结论；方案任务说明推荐方向。
- **关键内容**：实施任务列出关键变更；只读任务列出关键发现；方案任务列出关键决策。
- **依据与影响**：Bug/CI 任务说明根因；分析与审查说明证据和影响；不适用时写“无”。
- **核查与验证**：列出已执行的命令、检查或交叉核对；未执行时说明原因和可执行的验证方式。
- **风险与后续**：列出遗留风险、限制和需要用户决定的下一步；没有时写“无”。

`.aitasks` 的 todo 和经验模板由 `aitasks-maintenance` 唯一维护。仅在需要维护写入时使用该专项 Skill；新建记录只读取对应模板，更新状态或计数无需模板。不得在入口复制或另建模板。
