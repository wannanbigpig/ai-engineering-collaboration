## 确认的问题与讨论后的修法

1. 多个 Harness 的 `skills` 路径指向同一共享目录时，预检分别计划同名链接，首次安装执行到第二个别名会失败。两位 Agent 确认该布局属于现有支持范围；现在仅在链接已精确指向预期 canonical 时视为完成，其他目标仍保留冲突保护。项目和用户范围均先复现失败，再验证预览、初装、幂等与安装检查。
2. 批次启动后 CLI 自更新仍可能被记为完成。真实临时可执行文件已复现其摘要变化、实例却 `completed` 的情况。现在每次调用前后核对同一批次的运行器、CLI 和运行条件摘要，漂移保留轨迹及工作区后记为 `runner_error`。报告仅核归档观测，不因当前机器后来升级而否定历史证据；缺少观测的旧实例保留汇总但不能冒充可信成本配对。
3. 新订单编号前向场景再次输出停用经验，并把代码围栏中的元数据示例误当记录边界。最终业务结论正确、文件未变，但流程失败，说明上一轮的文字澄清未稳定解决问题。讨论后否决继续追加临时解析规则，改为复用确定性实现。

只读解析与查询现由维护 Skill 的 `scripts/query_aitasks.py` 唯一维护，维护 CLI 直接导入；四个消费者随包提供字节和权限一致的生成副本及别名资产。`sync_query_tools.py --write` 负责生成，仓库校验和打包拒绝副本漂移。独立脚本仅提供 `context`、`get-record`、`list-todos`，不包含维护写入能力。无 Python 时只定位标题与元数据，未核实正文保持未验证，不临时再造经验解析器。

三方对照被截断的文档也已澄清：缺少基线或候选就不能比较双方；仅缺少无技能对照时，仍可报告完整双方配对，但不能给三方结论。

- Agent 调用自带查询脚本的 `context`，只返回有效及 legacy 摘要，再按 ID 调用 `get-record`。
