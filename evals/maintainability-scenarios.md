# 可维护性行为评测

这些场景验证 Skill 是否改变 Agent 的实际工程行为，而不只是检查 Markdown 中是否存在关键词。每个场景应在一次新的 Harness 会话和一次性 Git fixture 中执行；为被测 Harness 安装本仓库全部 Skill，并保留完整提示、工具调用、diff、测试输出和最终回复。

## 评测方法

1. 按场景建立最小 fixture，提交基线后再发出“用户请求”。除场景明确允许外，不额外提示被测 Agent 应选择哪个专项 Skill。
2. 根据“必须观察到”和“不得出现”逐项评分；全部必须项满足且没有禁止项才通过。
3. 评测证据必须来自实际工具调用、文件内容、diff 或测试输出。只在回复中声称执行过，不得判定通过。
4. 记录模型、Harness、Skill 版本、fixture commit 和执行日期。不同 Harness 的结果分别报告，不互相替代。

## 复用已有实现

### Fixture

- `src/orders/filter.py` 已提供日期范围校验与模糊匹配函数，并有调用方和测试。
- `src/refunds/view.py` 尚未实现相同筛选需求。

### 用户请求

> 给退款列表增加与订单列表相同的日期范围和模糊匹配筛选，并完成验证。

### 必须观察到

- 修改前检索并打开订单筛选实现、调用方和相关测试。
- 优先复用或扩展已有实现；如果保持重复，说明业务边界和耦合风险依据。
- 验证订单与退款两个调用路径。

### 不得出现

- 未检索现有实现就直接在退款模块生成第二套等价逻辑。
- 仅因代码相似就进行超出目标范围的全仓抽象。

## 影响分析优先

### Fixture

- 一个公共序列化函数被 API、队列消费者和导出任务共同调用。
- 现有测试只覆盖 API。

### 用户请求

> 调整 API 返回中的日期格式，并完成修改。

### 必须观察到

- 修改前找到公共函数的全部相关调用方，并识别队列和导出契约风险。
- 选择局部适配或在获得明确契约后修改共享实现。
- 验证范围覆盖实际受影响路径，无法执行的路径标记未验证。

### 不得出现

- 只根据 API 入口修改共享函数并宣称全部完成。
- 为绕开共享实现新增一个没有迁移计划的 `v2` 平行函数。

## 错误处理语义

### Fixture

- 外部请求代码使用空 `catch` 返回空数组。
- 业务约定中“未找到”允许空数组，超时和鉴权失败必须保留不同错误语义。
- 请求参数含有访问令牌。

### 用户请求

> 修复请求失败时没有可观测信息的问题，并补测试。

### 必须观察到

- 区分“未找到”、超时和鉴权失败，而不是统一处理。
- 非预期异常保留 cause 或等价诊断链路，并覆盖关键失败路径测试。
- 日志或错误信息对访问令牌脱敏，只记录定位所需的最小上下文。

### 不得出现

- 所有错误一律抛出或一律返回空数组。
- 将完整请求入参、令牌或凭据写入日志和异常。

## 量化指标证据

### Fixture

- 项目没有配置重复度或圈复杂度分析器，只有普通单元测试和 Lint。

### 用户请求

> 完成改动后告诉我重复率、圈复杂度和测试覆盖率。

### 必须观察到

- 先检查项目是否已有对应工具和配置。
- 只报告实际命令得到的数字，并附工具、版本、范围和输出依据。
- 缺少工具时明确标记指标未验证，可给出安装或执行建议但不擅自扩大依赖。

### 不得出现

- 根据阅读代码估算百分比并写成测量值。
- 用测试通过或 Lint 通过替代覆盖率、重复率或复杂度数据。

## 避免过度拆分

### Fixture

- `src/refunds/service.py` 中的退款处理函数按“校验、加载、计算、写入、发布事件”顺序组织，主流程可在一处阅读。
- 函数约 70 行，其中两个条件分支复杂，但多数步骤只服务于这条流程；项目没有函数行数上限。

### 用户请求

> 这个函数太长了，帮我重构得清晰一些并完成验证。

### 必须观察到

- 修改前检查复杂度、内聚性、调用方与项目惯例，不把函数行数直接当作拆分依据。
- 保持主流程可顺序阅读；只在形成独立业务概念、真实复用、测试或副作用边界，或实质降低复杂度时提取函数。
- 说明保留连续代码和提取函数的依据，并验证行为没有变化。

### 不得出现

- 仅为缩短行数，把每个顺序步骤拆成单次使用、只转发参数的薄包装函数。
- 将同一流程的辅助函数散落到多个文件，增加无收益的调用跳转和上下文恢复成本。

## 沿用后端主流风格

### Fixture

- 项目的订单和客户模块都使用 `Request -> Service -> Resource` 分层、统一错误响应和同一种测试组织方式，仓库配置了 formatter 与 Lint。
- 一个较早的遗留模块把 SQL 和响应拼装都写在 Controller 中，但没有新模块继续采用这种方式。

### 用户请求

> 新增库存调整接口，按这个项目的方式实现并完成验证。

### 必须观察到

- 修改前读取适用规则、formatter/Lint 配置，并检查多个仍在使用的同类接口、共享基础设施和测试。
- 以目标模块主流实现确定分层、命名、校验、错误、事务和测试方式，复用现有扩展点。
- 运行项目已有的格式化、Lint 和相关测试，偏离现有模式时给出需求或技术依据。

### 不得出现

- 只看一个遗留 Controller 就复制旧写法，或只凭通用最佳实践引入项目没有的新分层和依赖。
- 为了统一风格顺带重构无关的遗留模块。

## 无设计稿时沿用现有 UI

### Fixture

- 前端已有订单和客户列表页，共用 `PageContainer`、`DataTable`、`FormDrawer`、主题令牌以及加载、空和错误状态组件。
- 新退款页面没有设计稿，用户允许 Agent 自行布局。

### 用户请求

> 新增退款管理页面，具体布局你自行处理，完成后验证。

### 必须观察到

- 修改前检查同类页面、公共组件、主题/样式配置和交互模式，说明选择的参照依据。
- 复用现有页面容器、组件与设计令牌，并保持权限、反馈、响应式及加载/空/错误状态一致。
- 除构建与类型检查外，在浏览器能力可用时打开实际页面并与参照页面进行视觉核对；不可用时明确标记 UI 未验证。

### 不得出现

- 无依据地增加组件库、全局样式、硬编码颜色或一套不同的页面布局和交互语言。
- 仅凭编译、构建或单元测试通过就声称 UI 风格一致。
